# 04 — Cross-model comparison table

Status: done

## Parent

[M4 PRD](../PRD.md)

## What to build

Run the same rung, the same candidate lists, and the same prompt against every model ADR-0008 named. Then build a table that compares them on accuracy, cost, and latency.

This is the milestone's second deliverable, and it answers a different question from issue 03. Issue 03 asks *does reranking help?* This asks *how much model do you need before it does?* A cheap model that recovers most of a frontier model's gain at a fraction of the price is the more useful engineering result. Nobody can claim it without measuring both.

Write one `RESULTS.md` entry per model, so each figure keeps its own provenance. The table is a view over those entries. Never type a number into it by hand.

## Acceptance criteria

- [x] Every model from ADR-0008 runs on the full dev split, each with its own `RESULTS.md` entry
- [x] The table reports Top-1 with interval, Recall@3, Recall@5, cost per instance, and latency per model
- [x] The table reports total spend per model, and the actual figure against ADR-0008's estimate
- [x] The table states overlapping intervals explicitly. At n=244 the intervals are ±6pp, so most pairs will not separate
- [x] Per-repo breakdown for at least the best and the cheapest model. M3 showed that the aggregate hides redistribution
- [x] Failure modes counted per model: unparseable responses, and files returned that were not candidates
- [x] Every figure traces to a `RESULTS.md` entry. Check this by string match rather than by eye

## Notes

The interval problem is sharper here than anywhere else in the project. Three models at n=244 give three overlapping intervals. A table sorted by point estimate reads as a ranking whether or not a ranking exists. State plainly what the measurement establishes and what it does not, as the M3 README does.

If the models are indistinguishable on accuracy, **that is the result**. It makes the cheapest one the right choice, which is a stronger engineering claim than a frontier model that wins by a point.

Cost per instance is the number that makes this table worth building. Report it beside accuracy in the same row. Never put it in a footnote.

### What this establishes

**That paying more does not buy accuracy here.** The four cells span an 11.8x price difference per token and 2.5x in actual spend, and land within 6.6 points of each other with intervals overlapping almost entirely. Issue 04's Notes anticipated exactly this: *if the models are indistinguishable on accuracy, that is the result* — and it makes the cheapest one the right choice, which is a stronger engineering claim than a frontier model winning by a point.

The measurement was built to be capable of showing otherwise. ADR-0008's first amendment widened the model pair from 1.5pp apart on a public benchmark — inside this project's own +/-6pp interval — to 11.8x apart on price. Without that change the null result would have been unreadable: indistinguishable, but indistinguishable from what?

**That reasoning effort is not worth its price on this task.** Both ablations agree, and neither can be attributed to the other: DeepSeek gains 4.1pp for 58% more spend, gpt-oss gains 1.7pp for half the spend. Every one of those gaps is inside the interval.

### What it does not establish

**Any ordering among the four.** `rerank-deepseek-on` leads on the point estimate and its interval overlaps every other cell. A table sorted by score would read as a ranking; the rows are therefore ordered as the ladder is, not by result.

**That the cheapest configuration is best.** `rerank-deepseek-off` is cheapest *and* second on points, which is suggestive and nothing more. It also produced 43 off-list paths, three times the ladder row's rate.

**Anything about latency.** Wall clock is in the table because the criteria ask for it, but it is not comparable across rows: `rerank` includes cache replay across four restarts, and DeepInfra ran 5x slower than DeepSeek's own endpoint throughout. The column measures the provider, not the model.

### The estimates were unreliable in direction, not just magnitude

Three of four estimates came in low by 10-30%, which is tolerable. `rerank-deepseek-off` came in at a third of its estimate — and its *second* estimate, from a larger sample, was six times too low in the other direction. Small-sample cost projections here do not converge; they move.

This mattered. That cell's $0.95 estimate -- 3x what it actually cost -- was the single largest line in the projection that made all four cells look unaffordable, and it drove a budget renegotiation that turned out to be unnecessary. The four published rows came to $1.95 against a projection of $3.36.

### Per-repo, and the one repo where every model agrees

Sphinx is 63.6% in all four cells — the union Candidate Set's hit@20 for sphinx exactly. Rung 2.6's cross-encoder managed 18.2% on the same instances against the same ceiling, so this is not a ceiling artefact: it is where reading twenty candidates together in language solves what scoring them one at a time does not.

The redistribution M3 warned about is visible elsewhere. `rerank-deepseek-off` beats `rerank-deepseek-on` on pytest (90.0% against 80.0%) while losing badly on pylint (25.0% against 75.0%) and requests (50.0% against 75.0%). Both are n=4 repos, so neither difference is a result — but it is the same pattern that made the aggregate misleading at M3, and it is why the per-repo line stays in every entry.
